# Поддержка фильмов в kwbooktrack — дизайн

Дата: 2026-11-16
Статус: на согласовании (ревизия 2 — после уточнения требований)

## 1. Зачем

В библиотеке Tellico (`movi.tc`) лежит коллекция фильмов — 18 записей с
обложками, жанрами, актёрами, продолжительностью, датой просмотра и рецензией.
Приложение умеет только книги. Пользователь хочет видеть фильмы в том же
приложении: тот же список с теми же фильтрами, календарь просмотров,
статистику времени просмотра, **те же заметки, цитаты, теги и фото**, редактирование
и импорт/экспорт без потери данных.

## 2. Границы

### Цели

- Отдельный домен «фильм»: список, карточка фильма, **редактирование**, календарь
  просмотров, статистика времени просмотра.
- Заметки, цитаты, рецензии, теги и фото — **для фильмов то же самое, что для
  книг**, теми же таблицами.
- Импорт `movi.tc` (родной формат Tellico, коллекция `type="3"`).
- Экспорт фильмов в оба формата: свой zip-бэкап и родной `.tc`.
- Переключение «Книги ⇄ Фильмы» дропдауном в заголовке списка (как в фильтрах).
- Время просмотра фильма = его `running-time` (минуты).
- Обложки — с именем-UUID у книг **и** фильмов, со совместимостью со старыми.

### Не цели

- Трекер страниц у фильмов (страниц у фильма нет). Сессии чтения — только у книг.
- Импорт CSV-выгрузки Tellico для фильмов (в `movi.tc` — XML).
- Перенос старых обложек на UUID-имена (см. §4.6 — не требуется).

### Анти-цели

- Не плодить вторую параллельную реализацию заметок/цитат/тегов/фото: у фильмов
  и книг **общие** таблицы.
- Не ломать работающее: книжный импорт/экспорт, статистика и календарь книг
  должны вести себя ровно как раньше.

## 3. Источник данных: `movi.tc`

`movi.tc` — zip с `tellico.xml` и `images/{md5}.{ext}` (18 обложек).
Коллекция `<collection title="Мои фильмы" type="3">`.

Разобранная структура записи (по реальному файлу):

| Tellico | Значение в файле | Тип |
|---|---|---|
| `title` | `<title>Малхолланд Драйв</title>` | текст |
| `year` | `<year>1999</year>` | число |
| `genre` | `<genres><genre>Триллер</genre></genres>` | много |
| `nationality` | `<nationalitys><nationality>США</nationality></nationalitys>` | много |
| `cast` | `<casts><cast><column>Уоттс, Наоми</column></cast></casts>` | **таблица**, 2 колонки «Актёр/актриса» + «Роль» |
| `director` | `<directors><director>Линч, Дэвид</director></directors>` | много |
| `producer` / `writer` / `composer` / `studio` | контейнеры `+s` | много |
| `running-time` | `<running-time>147</running-time>` | число, **минуты** |
| `plot` | `<plot>…</plot>` | многострочный |
| `rating` | `<rating>5</rating>` | 1..5 |
| `keyword` | `<keywords><keyword>…</keyword></keywords>` | много |
| `cover` | `<cover>04f7b153….jpeg</cover>` | имя файла в архиве |
| `comments` | `<comments>…</comments>` | многострочный |
| `дата-просмотра` | `<дата-просмотра calendar="gregorian">…` | дата |
| `оригинальное-название` | `<оригинальное-название>Mulholland Dr</…>` | текст |
| `кинопоиск` | `<кинопоиск>https://www.kinopoisk.ru/film/466/</…>` | URL |
| `скачан` | `<скачан>true</скачан>` | флаг |
| `рецензия` | `<рецензия>…</рецензия>` | многострочный |
| `cdate` / `mdate` | дата Tellico | дата |
| `id` | `<id>1</id>` | служебный, игнорируется |

Факты, которые ломают наивную реализацию:

1. **Дата просмотра бывает неполной** — Tellico допускает `year`+`month` без
   дня (2 записи из 18) и даже только `year` (2 записи). Парсер дополняет
   1-м числом месяца и 1-м числом года — ровно как книжный `parseDate`. Фильм с
   датой «только год» считается **просмотренным** и попадает на 1 января
   (вариант «дата неизвестна ⇒ не просмотрен» отбросил бы фильм, который
   пользователь точно смотрел).
2. **Таблица `cast` записана «по-столбцам»**: `<cast><column>Актёр</column>
   <column>Роль</column></cast>`. Ридер берёт текст элемента через
   `textContent()`, а он склеивает **вместе с whitespace** между потомками —
   выходит «Уоттс, Наоми\n     Роль»: перевод строки внутри значения плюс
   потерянная граница «актёр / роль». В реальном файле 20 из 83 строк `cast`
   имеют обе колонки. **Ридер надо чинить**: у элемента, у которого есть
   потомки `<column>`, брать тексты колонок и соединять их `::`, а не
   `textContent()`.
3. `<images>` лежит **внутри** `<collection>` — так и пишет текущий writer.
4. **Один `.tc` — одна коллекция.** DTD v12 формально разрешает несколько
   (`<!ELEMENT tellico (collection+, …)>`), но реализация Tellico этого не
   умеет. Разобрал исходники `src/translators/xmlstatehandler.cpp`
   (Tellico 3.4.6 и 4.3, Debian sources):

   - `StateData::coll` — **одна** коллекция; каждый блок `<fields>` делает
     `d->coll = CollectionFactory::collection(type, addFields)`, то есть
     перезаписывает предыдущую;
   - `StateData::entries` — только пополняется (`d->entries.append(entry)`) и
     **не очищается** между коллекциями;
   - `CollectionHandler::end()` делает `d->coll->addEntries(d->entries)`.

   Итог для файла с двумя `<collection>`: Tellico создаёт коллекцию **последнего**
   типа и добавляет в неё записи **обеих** коллекций — книги окажутся внутри
   коллекции фильмов. Это повреждение данных, а не «Tellico проигнорирует
   вторую коллекцию».

   Значит, `.tc` должен содержать **ровно одну** коллекцию — ровно так же, как
   выгружает сам Tellico.
5. **В коллекции фильмов Tellico нет полей для заметок.** Зато есть `рецензия`.
   Значит, наши собственные поля (`цитаты`, `заметки`, `теги`, `фото-заметок`)
   надо **дописать** в `<fields>` коллекции фильмов при экспорте — иначе
   Tellico молча выбросит значения, и заметки фильма не переживут round-trip.

## 4. Модель данных

### 4.1 Тип носителя

```kotlin
enum class MediaType { BOOKS, MOVIES }
```

`MediaType` — это «к какому типу относится запись, к которой привязана
заметка/тег/фото». Хранится как `String` (конвертер, как `BookStatus`).

### 4.2 Таблица `books` — без изменений

Книги остаются в своей таблице. `BookEntity`, `BookDao`, `BookRepository` не
трогаем, кроме передачи `MediaType.BOOKS` в заметки/теги/фото.

### 4.3 Новая таблица `movies` (миграция v9 → v10)

```
id                INTEGER PK AUTOINCREMENT
title             TEXT NOT NULL
original_title    TEXT
year              INTEGER
genre             TEXT          -- много значений, "; "
nationality       TEXT          -- много значений, "; "
director          TEXT          -- много значений, "; "
cast              TEXT          -- строки "\n", ячейки "::"
duration_min      INTEGER       -- running-time, минуты
rating            INTEGER       -- 1..5
watched_at        INTEGER       -- дата просмотра
cover_path        TEXT
plot              TEXT
comments          TEXT          -- comments из Tellico
url               TEXT          -- кинопоиск
is_downloaded     INTEGER NOT NULL
created_at        INTEGER NOT NULL
updated_at        INTEGER NOT NULL
source            TEXT NOT NULL
title_search      TEXT NOT NULL  -- title + original_title, lowercase
people_search     TEXT NOT NULL  -- director + cast, lowercase
extra_fields      TEXT NOT NULL  -- JSON, всё что не стало колонкой
```

Индексы: `title_search`, `people_search`, `watched_at`.

**Рецензии нет отдельной колонки** — рецензия фильма это заметка
`kind = REVIEW`, ровно как у книг. Отдельная колонка означала бы, что рецензия
фильма и рецензия книги живут в разных местах и по-разному показываются.

`status` у фильмов не используется: «просмотрен / не просмотрен» определяется
по `watched_at`.

Два «поисковых» столбца — по образцу книжных `title_search`/`author_search`:
SQLite `LIKE` не складывает кириллицу регистронезависимо, поэтому поиск идёт
по предвычисленным `lowercase()`-строкам.

`cast` хранится в том же виде, в котором его отдаёт ридер (строки `\n`,
ячейки `::`) — так не теряется граница «актёр / роль», и обратная выгрузка
в Tellico получается тривиальной.

`extra_fields` — **тот же** `Map<String, ExtraField>`, что у книг
(`{"<имя>": {"t": <заголовок>, "v": <значение>}}`): заголовок нужен при
экспорте в `.tc`, где чужие поля объявляются в `<fields>`, а при импорте
заголовок берётся из объявления поля в исходном файле. Отдельный формат для
фильмов означал бы, что заголовки теряются.

### 4.4 Общие заметки, цитаты, теги и фото

Три таблицы становятся «медиа-скоупированными»:

| Таблица | Было | Стало |
|---|---|---|
| `notes` | `book_id` FK → books | `media_id`, `media_type`, **FK на books убран** |
| `photos` | `book_id` FK → books, `note_id` FK → notes | `media_id`, `media_type`, `note_id` FK → notes (сохраняется) |
| `book_tags` | (`book_id`, `tag_id`) | `media_tags` (`media_id`, `media_type`, `tag_id`) |

`reading_sessions` **не трогаем**: сессии чтения — только у книг, их FK на
`books` остаётся и каскадит как раньше.

**Почему не «таблица-родитель `media`».** Вариант с общей таблицей
`media(id, media_type)` и `books.media_id → media(id)` сохранил бы внешние
ключи, но требует пересоздания `books` (38 колонок) и всех четырёх таблиц-потомков
с переносом данных — самый рискованный шаг во всей задаче, ради экономии
одной колонки в трёх небольших таблицах. Дискриминатор `media_type` дешевле:
пересоздаются только три маленькие таблицы, а большая `books` и её данные не
трогаются вообще.

**Цена: каскада больше нет.** Удаление книги или фильма обязано чистить
заметки, фото и привязки тегов вручную. Это делается в репозитории рядом с
уже существующей ручной чисткой файлов фото:

```kotlin
// BookRepository.delete
noteRepository.deleteForMedia(id, MediaType.BOOKS)
photoRepository.deleteFilesForMedia(id, MediaType.BOOKS)   // файлы
photoRepository.deleteForMedia(id, MediaType.BOOKS)         // строки
tagRepository.clearForMedia(id, MediaType.BOOKS)
coverStorage.delete(book.coverPath)
```

Порядок: сначала заметки (иначе `photos.note_id` получит `NULL` по SET_NULL),
потом фото, потом теги, потом сама книга.

### 4.5 Доступ к данным

`MovieDao` + `MovieRepository` — по образцу `BookDao`/`BookRepository`:
`observeAll`, `getAll`, `findById`, `search` (raw SQL по `title_search` и
`people_search`), `insert`, `update`, `delete`, `upsertFromImport`.

Ключ слияния при импорте — **название + год** (у фильма нет ISBN):
`findByTitleAndYear`. Повторный импорт `movi.tc` не плодит дубли.

`MediaSource` — переименование `BookSource` (MANUAL/TELLICO/BOOKMORY/CATALOG):
имя перестало соответствовать смыслу, когда у таблицы `movies` появился свой
`source`. Переименование чисто механическое, значения в БД не меняются (это
`name` енума), полноту проверяет компилятор.

`MediaTypeStore` — синглтон с `StateFlow<MediaType>` (по умолчанию `BOOKS`).
Один источник правды для экрана списка, календаря, статистики и окна экспорта:
переключил на «Фильмы» → календарь и статистика тоже про фильмы. Не
персистится (зависимости DataStore в проекте нет, а при перезапуске приложения
разумно открывать книги).

### 4.6 Обложки: UUID везде, старые — работают

Сейчас обложка книги — `filesDir/covers/{bookId}.{ext}`, и имя файла = ключ в
zip-архиве. Три проблемы: у фильмов своя нумерация id (конфликт `1.webp` у
книги 1 и фильма 1), и имя по id привязывает файл к строке БД.

**Решение: имя файла обложки — UUID, у книг и фильмов одинаково.**
`filesDir/covers/cover_{uuid}.{ext}`.

- `FileCoverStorage.saveTemp` уже пишет `cover_{UUID.randomUUID()}.{ext}` —
  менять почти ничего.
- `promoteToBook(bookId, tempPath)` → `promote(tempPath)`: имя уже уникальное,
  копировать и переименовывать не нужно. `bookId` из интерфейса уходит.
- `deleteForBook(bookId)` → `delete(path)`: по префиксу `"$bookId."` больше
  не найти, удаляем по точному пути (путь лежит в `cover_path`).

**Совместимость со старыми данными.** В БД лежит **абсолютный путь** к файлу
обложки, а не имя. Поэтому старые файлы `{bookId}.{ext}` продолжают работать
как есть — переименовывать их не нужно, миграция по обложкам не требуется
вообще. Новые обложки получают UUID-имена; старые лежат рядом и удаляются
по своему пути.

В zip-архиве ключ обложки — имя файла, поэтому `cover_{uuid}.webp` у книг и
фильмов не конфликтует, а старые `1.webp` конфликтуют только с другими
старыми `1.webp` — их и раньше не могло быть два.

## 5. Импорт

### 5.1 Ридер

`TellicoXmlReader` сейчас жёстко ищет коллекцию `type="2"` и бросает
«Это не коллекция книг» на всё остальное. Меняем на:

- читаем **все** коллекции файла, но обрабатываем **только `type="2"` (книги)
  и `type="3"` (фильмы)**;
- коллекции других типов (библиография `type="1"`, игры `type="4"` и прочие)
  **пропускаем**: у библиографии поле года называется `year`, а не `pub_year`,
  и без разбора она превратилась бы в книги — это ломает книжный импорт;
- если в файле нет ни одной поддерживаемой коллекции — ошибка «Это не
  коллекция книг и не фильмов»;
- тип коллекции (`type`) пишем в `TellicoRecord.collectionType` (по умолчанию 2);
- набор «известных» полей зависит от типа: для `type="3"` — словарь полей
  фильмов, для остальных — книжный `TellicoFields.KNOWN`;
- **правка `cast`**: элемент с потомками `<column>` — тексты колонок соединяем
  через `::` (§3, п. 2).

`TellicoRecord` получает поле `collectionType: Int = 2` — обратно совместимо,
CSV-ридер его не задаёт.

Тест `TellicoXmlReaderTest.nonBookCollectionIsRejected` меняется: `type="1"`
(библиография) теперь отвергается, а `type="3"` читается.

### 5.2 Маппер фильмов

`TellicoMovieMapper` — по образцу `TellicoBookMapper`. Пробегает поля
коллекции фильмов и строит `MovieEntity`:

| Tellico | MovieEntity |
|---|---|
| `title` | `title` (пусто → «(без названия)») |
| `оригинальное-название` | `originalTitle` |
| `year` | `year` |
| `genre` / `nationality` / `director` | одноимённые колонки (много значений → `"; "`) |
| `cast` | `cast` — строки `\n`, ячейки `::` |
| `running-time` | `durationMin` |
| `rating` | `rating` (только 1..5) |
| `дата-просмотра` | `watchedAt` (неполная дата → 1-е число) |
| `cover` | `coverPath` (имя файла в архиве) |
| `plot` | `plot` (HTML → markdown, как `comments` у книг) |
| `comments` | `comments` |
| `рецензия` | заметка `kind = REVIEW` |
| `кинопоиск` | `url` |
| `скачан` | `isDownloaded` |
| `cdate` / `mdate` | `createdAt` / `updatedAt` |
| `теги` / `цитаты` / `заметки` / `фото-заметок` | заметки, теги, фото — **если коллекция их объявляет** |
| всё остальное | `extraFields` |

### 5.3 Применение

Фильмы применяются отдельным `MovieSnapshotApplier`: найти по названию+году →
слить или вставить → заметки/теги/фото (как у книг) → скопировать обложку из
архива в WebP 600px (та же воронка) под UUID-именем.

### 5.4 Маршрут импорта

`ImportTellicoUseCase` разводит записи по `collectionType`:
`type="2"` → книжный маппер, `type="3"` → маппер фильмов. Результат
импорта получает счётчик `movies`.

## 6. Экспорт

### 6.1 Родной `.tc`

**Один файл — одна коллекция.** Экспорт `.tc` выгружает коллекцию **текущего
типа носителя**:

- в режиме «Книги» → `<collection type="2">` с книгами;
- в режиме «Фильмы» → `<collection type="3">` с фильмами.

Это ровно то, что делает сам Tellico, и единственный вариант, который Tellico
читает без искажений (см. §3, п. 4). Чтобы выгрузить обе коллекции, делают
два экспорта — переключив тип носителя. Экран «О приложении» показывает, какая
коллекция выгружается, и позволяет переключить тип прямо там.

Коллекция фильмов объявляет `<fields>` — **все** поля, которые пишем, иначе
Tellico молча выбрасывает значения. Это:

- поля Tellico для видео — сниматы с реальной коллекции (название, тип,
  формат, флаги), чтобы выгрузка читалась Tellico как родная;
- **наши собственные поля** `цитаты`, `заметки`, `теги`, `фото-заметок` — иначе
  заметки фильма не переживут round-trip (§3, п. 5).

Списки выбора (`medium`, `certification`, `region`, `format`, `color`) объявляем
**текстом**, как уже сделано для книжных «Переплёт»/«Состояние»: значение не
из списка Tellico выбрасывает молча, а потерять значение хуже, чем показать
его без выпадающего списка.

`cast` пишется родным для Tellico способом — `<casts><cast><column>…</column>
</cast></casts>`, как в самом `movi.tc`. Текущий `TellicoXmlWriter.table()`
такую форму не умеет (он пишет одну таблицу строкой через `::`), поэтому для
`cast` нужна отдельная ветка записи.

`<images>` — **внутри** `<collection>`, как сейчас и как в самом `movi.tc`:
коллекция в файле одна, значит и блок `<images>` один.

Если в БД нет фильмов, коллекция всё равно пишется — пустая, только с
`<fields>`. Так же ведёт себя сегодняшний экспорт книг при пустой библиотеке.

Наш **собственный** ридер продолжает читать все коллекции файла: это устойчивость
к ручным слияниям, и она ничего не стоит. Но мы такие файлы больше не создаём.

### 6.2 Свой zip-бэкап

`manifest.json` + `books.csv` + **`movies.csv`** + `extra.json` + `covers/` +
`photos/`. `extra.json` получает секцию `movies` (ключ — id фильма) с
`extraFields`, заметками, тегами и фото — по образцу книжной. Старые бэкапы
читаются: новые поля `ExtraArchive.movies` и `ExportCounts.movies` имеют
значение по умолчанию.

**Обратная совместимость манифеста.** `ExportCounts` сейчас не имеет значений
по умолчанию ни у одного поля, а `manifest.json` декодируется с
`ignoreUnknownKeys = true` — но **без** `encodeDefaults`. Обязательное новое
поле `movies: Int` без значения по умолчанию уронило бы `MissingFieldException`
на **старом** `manifest.json`, то есть импорт старого бэкапа перестал бы
работать вовсе. Поэтому `movies: Int = 0`.

### 6.3 Импорт своего zip-бэкапа

Экспорт без импорта — это «импорт/экспорт без потери данных», которого нет.
Импортёр zip (`ImportKwBooktrackZipUseCase`) читает и `movies.csv`, и секцию
`movies` в `extra.json`:

- `movies.csv` — те же правила, что у `books.csv`: заголовок `;`, поля в
  кавычках, даты ISO;
- `extra.json` → `ExtraArchive.movies` (по id фильма) — заметки, теги, фото и
  `extraFields`;
- обложки фильмов ищутся по имени файла — тот же `findFile`, что у книжных.

Старые бэкапы (без `movies.csv` и без секции `movies`) читаются как обычно:
секция отсутствует → ни одного фильма.

## 7. Статистика и календарь

### 7.1 Календарь

Ключ даты — `watchedAt`. В ячейке фильма показывается обложка; второй режим
ячейки — **минуты просмотра** вместо страниц. Минуты фильма = его
`durationMin`; сумма за день = сумма по просмотренным в этот день фильмам.

Режимы календаря переименованы из «Книги/Страницы» в «Обложки/Значение»:
в режиме фильмов второй вариант называется «Минуты».

### 7.2 Статистика

Для фильмов: «Фильмов просмотрено: N», «Минут просмотрено: M» и два графика —
«Просмотрено фильмов по месяцам/годам» и «Минут просмотра по месяцам/годам».
Графики «куплено» и «потрачено» только у книг: в коллекции фильмов Tellico
есть цена, но нет даты покупки, агрегировать нечего.

`MovieStatsCalculator` — отдельный объект рядом с `StatsCalculator`:
книга и фильм считают разные величины, общий код — только группировка по
месяцам/годам, ради которой второй калькулятор и заводится.

## 8. Интерфейс

### 8.1 Список: один экран на оба типа

`BookListScreen` + `BookListViewModel` превращаются в `LibraryScreen` +
`LibraryViewModel` (пакет `ui/library/`). Один экран, один поиск, один ряд
фильтров; содержимое зависит от типа носителя:

- **Заголовок** — дропдаун «Книги ⇄ Фильмы» (тот же `ExposedDropdownMenuBox`,
  что у фильтра «Тип»).
- **Поиск** — подсказка зависит от типа: «Поиск по названию, автору, ISBN…»
  / «Поиск по названию, режиссёру, актёру…». Сканер ISBN — только для книг.
- **Фильтр «Тип»** — свои варианты: книги «Все / Не прочитано / В процессе /
  Прочитано / Куплено», фильмы «Все / Просмотрено / Не просмотрено».
- **Фильтр «Период»** — общий: у книг по датам чтения/покупки, у фильмов по
  дате просмотра.
- **Карточки** — общая обложка, название, подзаголовок (автор / режиссёр),
  звёзды. У книг — прогресс-бар и статус, у фильмов — «147 мин» и жанры.
- **Пустое состояние и счётчик совпадений** — свои тексты.
- **FAB «+»** — свои: у книг «добавить книгу», у фильмов «добавить фильм».

Общие детали выносятся в `ui/common/`: `FilterDropdown` и `periodText`
(сейчас `private` в `BookListScreen.kt`), `PeriodOption`/`PeriodOptions`/
`FilterState` (сейчас в `BookListViewModel.kt`).

### 8.2 Карточка фильма и редактирование

Экран `ui/movies/MovieDetailScreen.kt`, маршрут `movies/{movieId}`:
обложка, название, оригинальное название, год, продолжительность, рейтинг,
жанры, страна, режиссёр, актёры, дата просмотра, сюжет, ссылка на Кинопоиск.
Трекера страниц нет. Действия — редактирование и удаление.

Экран `ui/movies/MovieEditScreen.kt`, маршруты `movies/new` и
`movies/{movieId}/edit` — по образцу `AddBookScreen`: те же поля обложки,
рейтинга и тегов, но поля фильма.

**Заметки, цитаты, рецензия, теги и фото** — как у книг: те же экраны
`NoteEditorScreen`/`NoteDetailScreen`/`PhotoGalleryDialog`, те же таблицы.
Их «владелец» — теперь пара `(mediaId, mediaType)`, а не `bookId`.

Общие куски UI (секция заметок/цитат/тегов/фото, шапка с обложкой, выбор
обложки, звёзды рейтинга, редактор тегов) выносятся в `ui/common/` и
используются и книжным, и фильмовым экраном — это и есть «переиспользовать
код».

Маршрут редактора заметки получает `mediaId` и `mediaType`:
`notes/new?mediaId={mediaId}&mediaType={mediaType}&kind={kind}`.
Редактор **существующей** заметки тип владельца берёт из самой заметки.

### 8.3 Календарь, статистика, «О приложении»

Календарь и статистика — по одному экрану на оба типа: содержимое и подписи
зависят от `MediaTypeStore`.

Экран «О приложении»:
- в карточке «Библиотека» — счётчик фильмов;
- рядом с кнопкой «Экспорт в Tellico (.tc)» — переключатель «Книги ⇄ Фильмы»,
  чтобы было видно, какая коллекция выгружается (см. §6.1);
- сообщение об успехе — с числом книг или фильмов, а не только книг.

## 9. Миграции v9 → v10 → v11

Ручные миграции, как все предыдущие (`exportSchema = false`,
`autoMigrations = []`, `fallbackToDestructiveMigration` не используется).
Их **две**, а не одна: пересоздание таблиц — самый рискованный шаг задачи,
и его не стоит смешивать с созданием новой таблицы. Room выполняет обе
миграции в одной транзакции при обновлении — то есть для пользователя это
одна атомарная операция.

### 9.1 `Migrate9To10` — заметки, теги и фото становятся media-скоупом

1. Страховка содержимого `photos` во временную таблицу: у `photos` есть FK
   на `notes`, а `notes` сейчас пересоздаётся — при `DROP TABLE notes`
   внешний ключ `SET NULL` обнулил бы `photos.note_id`. Копия — как в
   `Migrate7To8`.
2. Пересоздать `notes` → `media_id` + `media_type`, **без** FK на `books`.
   Строки копируются как есть: `media_type` = `BOOKS`, `media_id` = прежний
   `book_id`.
3. Пересоздать `photos` → `media_id` + `media_type`; FK `note_id` → `notes(id)`
   SET_NULL сохраняется.
4. Пересоздать `book_tags` → `media_tags` (`media_id`, `media_type`, `tag_id`),
   FK на `tags` сохраняется, FK на `books` убран.
5. Вернуть `photos` из страховки.

Порядок важен: `notes` пересоздаётся раньше `photos`, потому что `photos`
ссылается на `notes`.

`reading_sessions` и `books` **не трогаем** — их данные и внешние ключи
остаются как были.

### 9.2 `Migrate10To11` — таблица `movies`

`CREATE TABLE movies` + три индекса (`title_search`, `people_search`,
`watched_at`). Данных нет, переносить нечего.

### 9.3 Проверка

- `Migrate9To10Test` по образцу `Migrate8To9Test` — создать v9-схему сырым
  SQL, заполнить книгой с заметками, тегами и фото, прогнать миграцию,
  проверить `PRAGMA table_info` и что все строки на месте.
- `Migrate10To11Test` — та же схема, проверка таблицы `movies` и индексов.
- Тест на **открытие Room'ом** мигрированной базы: Room проверяет схему при
  открытии и повалит любое расхождение (схемы не экспортируются,
  `MigrationTestHelper` не применим).

## 10. Решения, принятые за пользователя

| Вопрос | Решение | Почему |
|---|---|---|
| Статус фильма | Только «просмотрен / не просмотрен», по `дата-просмотра` | В Tellico у фильма нет поля статуса |
| Время просмотра | `running-time` фильма | Прямо просили; других источников длительности нет |
| Рецензия фильма | Заметка `kind = REVIEW`, как у книг | Прямо просили «как у книг»; отдельная колонка развела бы рецензии по разным местам |
| Заметки/цитаты/теги/фото фильмов | **Те же таблицы**, что у книг, + `media_type` | Прямо просили «как у книг» |
| Редактирование фильма | Есть, отдельный экран | Прямо просили |
| Неполная дата просмотра | Дополняем 1-м числом | Как в книжном `parseDate`; «неизвестно ⇒ не просмотрен» выбросило бы фильм, который смотрели |
| Коллекции других типов в `.tc` | Пропускаем | У библиографии `year` вместо `pub_year` — без разбора стала бы книгами |
| `.tc` — одна коллекция | Экспортируем коллекцию текущего типа | Tellico держит одну коллекцию на файл: две в одном файле смешают записи (§3, п. 4) |
| Фильмы в zip-бэкапе | Да, вместе с книгами | Формат наш, Tellico его не читает — можно держать обе коллекции |
| Имя файла обложки | UUID у книг и фильмов | Имя по id конфликтует между книгами и фильмами; старые файлы продолжают работать, миграция не нужна |
| `extra_fields` фильмов | Тот же `Map<String, ExtraField>`, что у книг | Заголовок нужен для объявления поля в `<fields>` при экспорте `.tc` |
| Счётчик фильмов в `manifest.json` | `ExportCounts.movies = 0` | Обязательное поле без значения по умолчанию уронило бы импорт старых бэкапов |
| Полиморфизм заметок | Дискриминатор `media_type` в трёх таблицах | Таблица-родитель `media` потребовала бы пересоздания `books` (38 колонок) с переносом данных — самый рискованный шаг задачи |

## 11. Что осознанно не делаем

- Широкоэкранное/цветность/режиссёрская версия/носитель не выводятся на
  отдельных экранах — лежат в `extraFields`, переживают импорт-экспорт.
- Сессии чтения у фильмов не заводим (нет трекера страниц).
- Не переименовываем старые файлы обложек на UUID-имена (в БД абсолютный
  путь — и так работает).
- Не добавляем `width`/`height` в `<image>` при экспорте — это отдельная
  тема, существующий экспорт книг с этим живёт.

## 12. Порядок работ

1. **Данные**: `MediaType`, миграция v9→v10, `movies` + DAO + репозиторий,
   полиморфизм заметок/тегов/фото, обложки на UUID.
2. **Импорт/экспорт**: ридер (обе коллекции + правка `cast`), маппер фильмов,
   writer `.tc` (коллекция фильмов со своими полями), zip-бэкап (экспорт +
   импорт).
3. **Интерфейс**: `LibraryScreen` с дропдауном, карточка фильма, редактирование
   фильма, календарь и статистика по типам, «О приложении».
